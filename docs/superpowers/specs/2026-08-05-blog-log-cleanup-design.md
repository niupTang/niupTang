# 博客日志整体清理设计

日期: 2026-08-05
仓库: niupTang/niupTang
目标: 做一次整体清理，覆盖文章归档、分类标签、乱码旧文、重复目录文件。

## 背景

当前博客是 Hexo 站点，核心文章位于 `source/_posts`。主分支当前可见内容包含数百篇公众号/AI 工具文章，另有根目录和 `source/` 下的目录型文件、工具脚本、主题和部署配置。

已观察到的问题:

- 文章文件名多数由完整标题组成，长度不一，存在空格、符号、标题截断和少量日期化 slug 混用。
- 文章 front matter 的 `categories` 和 `tags` 粒度不一致，部分旧文章仍是 `公众号文章`、`原创` 等弱分类。
- 少量旧文存在明显编码损坏，例如标题或正文中出现 `�?`。
- 根目录和 `source/` 下存在重复内容型文件，例如 `公众号文章分类.md`。
- `source/_posts` 中混入非文章图片文件，应迁移到统一静态资源目录。

## 目标

本次清理完成后应满足:

- 所有有效文章仍在 Hexo 标准文章入口 `source/_posts` 下，避免主题和插件兼容风险。
- 文章 front matter 结构统一，至少包含稳定的 `title`、`date`、`categories`、`tags`，必要时包含 `permalink`。
- 文章分类收敛为少量稳定一级分类，标签保留细颗粒度主题词。
- 乱码旧文不被误修正文；可确定的信息自动修复，无法可靠恢复的文章进入报告清单。
- 重复目录文件只保留一个公开入口，非公开副本移入维护资料或删除。
- 混在 `source/_posts` 的图片迁移到 `source/images/posts/`，文章引用同步更新。
- 提供可重复运行的审计/清理脚本和报告，后续新增文章可继续检查。
- `npm run build` 能完成 Hexo 构建。

## 非目标

- 不重写文章正文观点和文案。
- 不按年份或分类把文章文件移出 `source/_posts`，除非 Hexo 配置另行调整。
- 不批量替换外部公众号图片链接。
- 不删除无法判断价值的旧文章，只标记或隔离。
- 不处理大二进制资产和 PPT 模板。

## 分类规则

一级分类限定为:

- `AI工具`: 通用 AI 产品、客户端、效率工具、内容工具。
- `开源项目`: 以 GitHub 开源项目推荐、Star 盘点、项目榜单为主。
- `AI编程`: Claude Code、Cursor、Codex、MCP、Agentic Coding、代码生成和开发流程。
- `自动化`: 工作流、RPA、爬虫、内容同步、批处理、发布自动化。
- `教程实践`: 安装部署、实战教程、本地部署、API 接入、案例复盘。
- `副业案例`: AI 副业、内容变现、项目赚钱案例。
- `个人记录`: 年度总结、感想、说明、避坑和非工具型个人记录。

分类选择策略:

- 优先使用 front matter 原有分类；若原分类过泛或乱码，再用标题、标签和正文开头关键词推断。
- `GitHub`、`Star`、`开源`、`项目` 强信号优先归为 `开源项目`。
- `Claude Code`、`Cursor`、`Codex`、`MCP`、`编程`、`代码` 强信号优先归为 `AI编程`。
- `Coze`、`n8n`、`RPA`、`工作流`、`自动化` 强信号优先归为 `自动化`。
- `部署`、`安装`、`教程`、`实战`、`手把手` 强信号优先归为 `教程实践`。
- 无法可靠推断时保留原分类，并在报告中标记。

## 标签规则

标签保持短词和主题词，不使用过宽泛的来源标签作为唯一标签。

规范化示例:

- `公众�?`、`公众号文�?`、`原创` 不作为核心标签；可删除或降级。
- `Github`、`github` 统一为 `GitHub`。
- `Deepseek`、`deepseek` 统一为 `DeepSeek`。
- `Claude code`、`claude-code` 统一为 `Claude Code`。
- `AI 编程`、`AI编程` 统一为 `AI编程`。

每篇文章目标标签数量为 2 到 6 个。自动分类无法生成足够标签时，保留原标签并标记。

## 文件命名和链接

文件名规范:

- 新规范为 `YYYY-MM-DD-short-slug.md`。
- 已符合日期 slug 的文章保持不动，除非 front matter 明显错误。
- 对中文长标题旧文，生成可读短 slug，优先使用英文/拼音关键词；无法稳定生成时使用日期加短 hash。

链接保护:

- 改名文章必须保留或新增 `permalink`，使用原 Hexo slug 对应路径，降低公开链接失效风险。
- 已有 `permalink` 不删除，只在明显乱码且可确定原意时修正。
- 文件名改动必须由脚本生成映射报告。

## 乱码旧文处理

乱码识别:

- 标题、front matter 或正文出现 `�?`。
- YAML 无法解析。
- front matter 缺失结束分隔符。
- 标题、分类或标签明显截断。

处理策略:

- front matter 中的弱乱码字段可自动替换为可推断值。
- 正文乱码不做猜测性大段修复。
- 严重乱码但仍可构建的文章保留在 `source/_posts`，添加 `cleanup_status: needs_review`。
- 无法构建或 YAML 损坏的文章移入 `source/_drafts/needs-review/`，同时生成报告。

## 重复目录文件

`公众号文章分类.md` 的处理规则:

- 保留 `source/公众号文章分类.md` 作为公开页面入口。
- 根目录 `公众号文章分类.md` 作为维护资料移入 `docs/archive/公众号文章分类.md`，或在内容完全一致时删除。
- 若两个文件内容不同，保留更完整版本，并在报告中记录差异来源。

其他根目录内容型 Markdown:

- 部署、安全、README 等项目文档保持根目录。
- 年度总结类内容若是文章，应进入 `source/_posts` 或 `source/` 页面；若是维护指南，进入 `docs/archive/`。

## 工具设计

新增 `tools/blog-cleanup.js`，提供三个模式:

- `audit`: 扫描文章、front matter、分类标签、乱码、重复文件、图片混放，生成 `reports/blog-cleanup-audit.json` 和 `reports/blog-cleanup-audit.md`。
- `apply`: 按规则修改 front matter、迁移图片、处理重复目录文件，并生成 `reports/blog-cleanup-changes.md`。
- `check`: 校验清理后的约束，包括分类白名单、重复 slug、乱码清单、图片混放、YAML 可解析。

脚本要求:

- 默认不改正文。
- 所有批量文件移动都写入映射报告。
- 对风险项只标记，不猜测性修复。
- 反复运行应保持稳定，不制造重复 front matter 或重复报告项。

## 验证

完成后必须运行:

- `node tools/blog-cleanup.js audit`
- `node tools/blog-cleanup.js apply`
- `node tools/blog-cleanup.js check`
- `npm run build`

验收证据:

- `source/_posts` 不再直接包含图片文件。
- 公开文章分类仅使用白名单分类，无法判断的文章在报告中明确列出。
- 根目录和 `source/` 不再保留重复的 `公众号文章分类.md`。
- 乱码旧文清单存在，且无法可靠恢复的正文未被大段自动改写。
- Hexo 构建通过。
